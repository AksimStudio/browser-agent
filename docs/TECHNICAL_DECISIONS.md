# Исследование и технические решения

## Цель

Сделать универсального браузерного агента, который получает задачу на естественном языке, самостоятельно исследует незнакомый сайт, выполняет многошаговые действия в видимом браузере и останавливается перед опасными операциями.

Главные ограничения: нельзя писать сценарии под конкретные сайты, передавать модели полный HTML или доверять модели выполнение необратимых действий без независимой проверки.

## 1. Автоматизация браузера: Playwright

Рассматривались Playwright, Puppeteer и Selenium.

Выбран Playwright, потому что он предоставляет:

- persistent browser context для сохранения cookie и ручной авторизации;
- Chromium в видимом режиме;
- viewport, привязанный к фактическому размеру окна, поэтому адаптивная вёрстка реагирует на resize;
- автоматическое ожидание готовности элементов;
- удобные locators, работу с вкладками, диалогами и динамическими страницами;
- хорошие диагностические сообщения при перекрытии или исчезновении элемента.

Puppeteer хорошо подходит для Chromium, но Playwright даёт более цельную модель ожиданий и browser context. Selenium универсален, но для Node.js MVP требует больше инфраструктуры и ручной синхронизации.

## 2. Язык: JavaScript, Node.js

Выбран JavaScript, потому что Playwright имеет зрелый Node.js API, а официальный OpenAI SDK поддерживает tool calling без дополнительного транспортного слоя. Один runtime упрощает установку, демонстрацию и обработку асинхронных событий браузера.

Python-прототип был удалён: две реализации увеличивали стоимость поддержки и могли расходиться по возможностям.

## 3. AI backend: Codex CLI и OpenAI API

По умолчанию используется Codex CLI. На каждом шаге отдельный `codex exec` получает ограниченное состояние и возвращает строго структурированное решение. Он работает в read-only sandbox и не управляет браузером напрямую.

OpenAI API реализован как альтернативный backend. Переключение выполняется через `AI_PROVIDER`, а оркестратор и браузерные инструменты остаются теми же.

Такое разделение позволяет демонстрировать проект через существующую авторизацию Codex и позднее подключить API-ключ без изменения архитектуры.

## 4. Извлечение данных со страницы

Полный HTML не отправляется модели. Browser Controller извлекает:

- заголовок и URL;
- ограниченный видимый текст;
- интерактивные элементы: ссылки, кнопки, поля, select и ARIA-роли;
- короткие подписи, типы, безопасные href и контекст ближайшей карточки;
- временные `ref`, по которым выполняются действия.

Локальный DOM sub-agent ранжирует элементы по словам из задачи, оставляет релевантный текст и сокращает список элементов. Это дешевле отдельного модельного вызова и детерминировано.

Ограничения контекста:

- до 5000 символов исходного текста страницы;
- до 3500 символов после локального отбора строк;
- до 100 элементов до фильтрации;
- до 50 элементов после ранжирования;
- до 7000 символов JSON интерактивных элементов;
- до 20 коротких заметок;
- до 6 последних результатов действий;
- старый DOM-снимок заменяется новым.

Codex thread ограничен четырьмя решениями, после чего создаётся свежий thread с текущим состоянием и краткой историей. Это сохраняет локальную последовательность плана, но не позволяет старым DOM-снимкам бесконечно увеличивать оплачиваемый контекст. При `resume` повторно не отправляются системные инструкции и схемы инструментов.

## 5. Tool/function calling

Модель не получает прямой доступ к Playwright. Она выбирает ровно один инструмент за шаг:

- `observe`, `web_search`, `navigate`, `back`;
- `click`, `click_near_text`;
- `type`, `select`, `press`;
- `scroll`, `wait`;
- `take_screenshot`, `remember`.

Codex возвращает решение по JSON Schema. Для OpenAI используются function tools. Оба backend нормализуются к одному сообщению, после чего оркестратор валидирует аргументы и вызывает Browser Controller.

Последовательные вызовы выбраны намеренно: параллельные действия над одной вкладкой могут инвалидировать `ref` и создавать гонки.

## 6. Динамические страницы, попапы и формы

После действий агент ждёт DOM content, короткий `networkidle` и исчезновение распространённых индикаторов занятости. Фиксированная задержка остаётся только ограниченным запасным механизмом.

После каждого действия сравнивается состояние страницы. Если клик перекрыт, модель получает структурированную ошибку `CLICK_BLOCKED`, описание перекрывающего элемента и безопасные варианты восстановления.

HTML-диалоги обнаруживаются по `role=dialog`, `aria-modal` и тегу `dialog`. Инструмент `dismiss_popup` умеет осознанно закрыть, отклонить или принять такой попап. Это не выполняется скрытно: решение остаётся частью журнала tool calls.

Видимые overlay-контейнеры и их кнопки описываются отдельно, а интерактивные элементы внутри overlay получают повышенный приоритет. После `CLICK_BLOCKED` оркестратор автоматически делает один диагностический screenshot и прикладывает его к следующему решению модели, не расходуя отдельный агентный шаг.

Если пользователь назвал сайт без URL, `web_search` последовательно пробует Bing, DuckDuckGo и Google. Результат принимается только при отсутствии признаков CAPTCHA и наличии видимых внешних ссылок. Это позволяет пережить антибот-блокировку одного поисковика, не ослабляя контроль навигации.

Повтор точно такого же неудачного действия блокируется оркестратором. Для карточек предусмотрен `click_near_text`, который сначала находит карточку по содержимому, затем кнопку внутри неё.

JavaScript-диалоги перехватываются отдельно и требуют решения пользователя. Новая вкладка автоматически становится активной страницей агента.

## 7. Security layer

Security layer находится между решением модели и Playwright. Он не зависит от того, какой backend выбрал действие.

Подтверждение требуется перед:

- оплатой и оформлением заказа;
- удалением, архивированием и отправкой в спам;
- отправкой и публикацией данных;
- отправкой отклика;
- вводом пароля или платёжных реквизитов.

Отклонённое действие запоминается до завершения задачи. Повторная попытка блокируется без нового выполнения.

## 8. Обработка ошибок

Ошибка инструмента не завершает задачу сразу. Оркестратор:

1. сохраняет структурированную причину;
2. запрещает точный повтор действия;
3. повторно наблюдает страницу;
4. передаёт модели обновлённое состояние;
5. предлагает выбрать другой инструмент;
6. завершает работу только при реальной блокировке или достижении лимита шагов.

Лимит в 40 шагов защищает от бесконечных циклов.

## 9. MCP

Для MVP MCP не используется. Все инструменты локальны, работают с одним Browser Controller и должны проходить через общий security layer. Добавление MCP создало бы дополнительный транспорт и поверхность разрешений без функциональной необходимости.

MCP имеет смысл на следующем этапе, если браузерные инструменты потребуется предоставить нескольким агентам или подключить внешние сервисы: почту, календарь, CRM либо удалённый browser service.

## 10. Рассмотренные риски

- DOM меняется после каждого действия — `ref` считаются временными.
- Содержимое страницы может содержать prompt injection — оно объявлено недоверенными данными.
- CSS-классы нестабильны — агент не получает заранее заданные селекторы сайтов.
- Модель может повторять ошибку — повтор блокируется кодом.
- Модель может придумать внутренний URL — Browser Controller программно разрешает URL из задачи, обнаруженный href или корень нового сайта и отклоняет остальные как `UNTRUSTED_URL`.
- Автоматический клик может вызвать необратимый эффект — его проверяет независимый security layer.
- CAPTCHA, ручной логин и неизвестный пользовательский выбор не обходятся автоматически.

## 11. Проверка решения

Автоматические тесты проверяют:

- ограничение контекста и замену старого снимка;
- кратковременную память;
- запрет повторного ошибочного действия;
- JSONL-ответ Codex;
- конфигурацию Codex/OpenAI;
- ранжирование DOM;
- классификацию опасных действий.

Для демонстрации предусмотрен локальный почтовый сценарий, позволяющий безопасно показать автономную работу и запрос подтверждения перед удалением.
